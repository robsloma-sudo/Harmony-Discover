# v0.9 — Learning Review Console preview

## Purpose
An internal staff-facing review surface for candidate learning signals. It is not part of the consumer's five-tab navigation and is not exposed as a public route in production.

## Included preview
`app/learning-console.tsx` contains:
- Sample learning candidates across cocktail, agave education, and wine education.
- Filters by review state.
- Evidence/sample-size context.
- Suggested research next steps.
- Local-only draft/defer interactions to demonstrate the review flow.
- Explicit warning that sample data is illustrative and decisions are not persisted.

## Required production workflow
1. Candidate is generated by the server-side evaluator from currently consented, minimized aggregates.
2. Quality gate checks cohort size, baseline, active-user denominator, app version, feature launches, and sampling bias.
3. Reviewer sees aggregate counts and source/evidence references, never raw individual histories or free-text conversations.
4. Reviewer can request research, defer, reject, or mark insufficient evidence.
5. Research task gathers authoritative sources and identifies knowledge gaps.
6. A separate improvement proposal documents exact target, evidence, expected outcome, and rollback.
7. Authorized approver accepts or rejects the proposal.
8. Implementation occurs in the relevant Harmony development environment.
9. Outcome measurement compares pre-defined metrics; unsuccessful changes can be reverted.

## Roles to implement
- `learning_viewer`: read candidate summaries and approved research outputs.
- `learning_reviewer`: request research, defer, reject, mark insufficient evidence.
- `learning_approver`: approve an improvement proposal; cannot approve own proposal.
- `learning_implementer`: implement approved change and record version/rollback reference.
- `learning_admin`: manage roles and retention policy; all changes audited.

## Guardrails
- No one-click "train Harmony" or direct canonical mutation.
- No user-level drill-down, raw questions, or exact location.
- Reviewer actions require an authenticated staff identity and immutable audit record.
- Sample UI currently uses local component state only; no server persistence or auth is wired.
